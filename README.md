# Сервис прогнозирования дефолта по кредитным картам
Проект представляет собой production-ready веб-сервис на базе Flask, предназначенный для прогнозирования вероятности дефолта клиента по кредитной карте. Сервис контейнеризирован, имеет правильную изолированную структуру, покрыт базовыми тестами и поддерживает A/B-тестирование двух версий моделей "из коробки".

Датасет: https://www.kaggle.com/datasets/uciml/default-of-credit-card-clients-dataset/data

## Архитектура и дизайн сервиса
### Монолит vs Микросервисы
В данном проекте выбран **монолитный подход** (весь ML-код, логика роутинга и API находятся в одном приложении внутри папки app/). **Обоснование**:

Простота деплоя: для учебного проекта и выкатки одного эндпоинта ```/predict``` микросервисная архитектура создала бы избыточную сложность в виде сетевых задержек и конфигурации.
Ресурсы: монолит потребляет меньше памяти, что критично при локальном запуске.В реальном крупном банке при наличии десятков моделей (кредитный скоринг, антифрод, LDAP) этот блок был бы выделен в отдельный микросервис, общающийся с core-системой по REST/gRPC.
Концепт брокеров сообщений (RabbitMQ)
При масштабировании сервиса на миллионы запросов синхронный вызов ```/predict``` станет узким местом. RabbitMQ решает эту проблему:

- Асинхронный инференс: Клиент отправляет заявку. Сервис кладет ее в очередь и сразу отвечает "Заявка принята". Фоновые воркеры делают предсказание и отправляют результат в БД.
- Батч-обработка: В ночные часы банк может прогонять через очередь весь портфель клиентов для пересчета рисков без перегрузки API.

## Логирование и мониторинг
В сервисе реализовано логирование запросов/ответов в формате JSON. Код написан так, чтобы в логах отсутствовали системные предупреждения (UserWarning), туда попадают только чистые бизнес-события. В production эти логи собирались бы стеком ELK (Elasticsearch, Logstash, Kibana):

- Logstash парсил бы JSON-логи из Docker.
- Elasticsearch индексировал бы их.В Kibana строились бы дашборды: RPS, средняя вероятность дефолта по версиям модели (мониторинг дрифта), количество ошибок.

## Обзор инструментов MLOps
- DVC (Data Version Control): Позволил бы отслеживать версии датасета. Мы бы сделали dvc add data/raw/data.csv и привязали к коммитам Git. Это гарантирует воспроизводимость данных.
- MLflow: Использовался бы на этапе обучения для логирования параметров моделей, метрик (ROC-AUC=0.7513) и артефакта .joblib. Это позволяет сравнивать эксперименты в UI вместо ручного создания файлов model_v1, model_v2.

## Бизнес-метрики
Помимо технических метрик (ROC-AUC, F1), для банка важны:

- Expected Loss Reduction (Снижение ожидаемых потерь): Рассчитывается как Сумма выданных кредитов * Вероятность дефолта. Если модель v2 снижает этот показатель на A/B-тесте, она выгодна.
- Approval Rate (Доля одобренных заявок) при неизменном риске: Показывает, сколько хороших клиентов мы одобряем, отсекая верхние X% рискованных. Чем выше показатель при низком дефолте — тем лучше скоринг.

## A/B-тестирование
### Постановка эксперимента
- Гипотеза: Модель v2 (Logistic Regression) позволит увеличить Approval Rate без роста дефолтов по сравнению с моделью v1 (Random Forest).
- Способ разделения трафика: Детерминированное хэширование client_id (MD5). Гарантирует, что один клиент всегда попадет в одну группу (нет "мерцания" решений).
- Распределение: 50% на 50% (четный хэш — v1, нечетный — v2).
- Продолжительность: Минимум 2-4 недели (для набора статистически значимого количества реальных дефолтов).

## Метрики и анализ
- Основная метрика: F1-score для класса дефолта. Баланс между точностью и полнотой.
- Дополнительная метрика: Recall (Полнота). В скоринге ложноположительный результат (FP — отказали хорошему) дешевле, чем ложноотрицательный (FN — выдали дефолтеру). Recall критически важен.
- Статистический анализ: Используется Z-test для двух пропорций (сравнение долей дефолтов в группах). Доверительные интервалы строятся методом Уилсона. Критерий успешности: p-value < 0.05.


##  Запуск проекта
### Локальный запуск (требует Python 3.11+)
1. Клонировать репозиторий и перейти в него.
2. Создать и активировать виртуальное окружение:
python -m venv venvsource venv/bin/activate  # для Windows: venv\Scripts\activate
3. Установить зависимости:
    ```
    pip install -r requirements.txt
    ```
4. Сгенерировать артефакты моделей:
    ```
    jupyter notebook notebooks/01_training.ipynb
    ```
5. Запустить сервис:
    ```
    python -m app.api
    ```


## Запуск тестов
Для проверки корректности эндпоинтов и логики A/B-тестирования запустите pytest:
```
pytest tests/test_api.py -v
```

docker pull enrichmentt/credit-scoring-api:v1

```
docker-compose down
```
